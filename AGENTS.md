# Memory bank: завод лабораторных работ (C / gcc)

Этот репозиторий — конвейер для лабораторных по программированию на языке C. Агент Cursor при решении задач **обязан** следовать правилам ниже.

## Студент и вариант по умолчанию

Если в задаче агента не указано иное, использовать:

| Поле | Значение |
|------|----------|
| ФИО | Черниенко Максим Александрович |
| Факультет | Факультет математики и компьютерных наук |
| Специальность | Фундаментальная математика и механика |
| Группа | 14-А |
| Вариант | **19** (для каждой задачи внутри любой лабораторной) |

Опционально в промпте можно переопределить `variant`, `student_name`, `group` и т.д. — тогда в `lab.json` указываются переданные значения.

## Источник условий

Условия задач и варианты 1–25 — в методичке (PDF «Лабораторные работы по программированию на языке С/C++», КубГУ). Для лабораторной работы №`X`, задачи №`N` берётся подпункт **`N.19`**.

## Структура каталога лабораторной

Каждая лабораторная живёт в папке:

```text
lab_<номер_лаб>_<номер_варианта>/
```

Пример: `lab_1_19` — лабораторная 1, вариант 19.

### Обязательные файлы

| Файл | Назначение |
|------|------------|
| `lab.json` | Метаданные отчёта (дисциплина, тема, студент, номер лабы, вариант) |
| `task_XX.c` | Исходный код задачи №XX (две цифры в имени) |
| `task_XX.json` | Условие, ввод/ожидаемый вывод, ссылка на `.c`, параметры сравнения |
| `task_XX.md` | Краткое объяснение алгоритма и кода (2–8 предложений) |

### Запрещено вручную править после сборки

Файл `REPORT.md` в папке лабораторной **генерируется GitHub Actions** (`scripts/lab_factory`). Не редактируйте и не коммитьте его вручную — меняйте исходники, JSON и пояснения; после merge в `main` CI добавит отчёт отдельным коммитом.

### Не создавать в корне

Не смешивать несколько лабораторных в одной папке. Одна папка = одна лабораторная + один вариант.

## Формат `task_XX.json`

```json
{
  "task_number": 1,
  "condition": "Текст условия варианта 19 из методички",
  "source": "task_01.c",
  "stdin": "3.0 4.0\n",
  "expected_stdout": "5.000000 36.869898 53.130102 90.000000\n",
  "compare": "normalize",
  "timeout_sec": 5,
  "compile_flags": ["-std=c11", "-Wall", "-Wextra", "-lm"]
}
```

Поля:

- `compare`: `exact` | `normalize` (trim, схлопывание пробелов, нормализация переводов строк) | `ignore_trailing_ws`
- `compile_flags`: по умолчанию `["-std=c11", "-Wall", "-lm"]`
- `expected_stdout` может быть строкой или массивом допустимых строк

## Требования к коду C

- Компилятор: **gcc** (локально часто MinGW на Windows)
- Каждая задача — отдельный `main` в своём файле
- Читать данные со **stdin**, писать результат в **stdout** (как в заданиях на ввод-вывод)
- Имена файлов: `task_01.c`, `task_02.c`, …

### Кириллица в консоли Windows (обязательно)

Чтобы русские приглашения отображались в консоли Windows, в **каждом** `task_XX.c`:

1. После стандартных `#include` добавить подключение Windows и вызов UTF-8 (кодовая страница **65001**):

```c
#ifdef _WIN32
#include <windows.h>
#endif
```

2. В **начале** `main` (до любых `printf`/`scanf`):

```c
#ifdef _WIN32
    SetConsoleOutputCP(65001);
#endif
```

Директивы `#ifdef _WIN32` обязательны в репозитории: CI собирает и тестирует код под **Linux/gcc**, где `windows.h` недоступен. На Windows (MSVC, MinGW) блок выполняется и включает UTF-8 для stdout.

Допустимая альтернатива — `#include "../../templates/lab_console.h"` (или свой путь) и вызов `lab_console_utf8();` в начале `main` (см. `templates/lab_console.h`).

### Дружественный интерфейс (обязательно)

Программа **не должна** молча ждать ввод. Перед **каждым** `scanf` (или чтением из stdin) выводите понятное приглашение на **русском**, что именно нужно ввести, например:

- `Введите число a: `
- `Введите нижнюю границу диапазона a: `
- `Введите шаг h: `
- `Введите элемент последовательности: ` (в цикле — перед каждой итерацией)

Правила:

1. Текст приглашения однозначно соответствует переменной или смыслу из условия задачи.
2. Приглашения идут в **stdout** (обычно `printf` + при необходимости `fflush(stdout)`).
3. В `task_XX.json` поле `expected_stdout` должно содержать **полный** вывод программы: все приглашения **и** итоговые данные (таблицы, ответ). `stdin` — только значения без текстов подсказок.
4. Запрещены «немые» программы без подсказок; декоративный мусор (баннеры, шутки) не добавлять — только осмысленные приглашения к вводу и требуемый результат.

## Порядок работы агента для новой лабораторной

1. Создать папку `lab_<L>_<V>` (обычно `V=19`).
2. Заполнить `lab.json` (или скопировать шаблон из `templates/lab.json`).
3. Для каждой задачи методички:
   - Выписать условие варианта **19** в `task_XX.json`
   - Написать `task_XX.c` с **UTF-8 консолью Windows** (`SetConsoleOutputCP(65001)`) и **дружественными приглашениями** перед каждым вводом, локально проверить:  
     `gcc -std=c11 -Wall task_XX.c -o /tmp/task -lm && printf '...' | /tmp/task`
   - Зафиксировать **полный** реальный вывод (приглашения + ответ) в `expected_stdout`
   - Написать `task_XX.md` с кратким разбором
4. Закоммитить и смержить в `main` — CI соберёт отчёт и закоммитит `REPORT.md`.

Локальная проверка всего конвейера:

```bash
python3 -m scripts.lab_factory --lab lab_1_19
```

## Сборка отчёта (CI)

При push в `main` workflow `.github/workflows/lab-reports.yml`:

1. Находит каталоги `lab_*_*`
2. Компилирует и запускает каждую задачу
3. При успехе формирует `lab_*/REPORT.md` (титульный лист + задачи: условие, код, ввод, вывод)
4. Коммитит изменения от имени `github-actions[bot]`, если отчёт обновился

## Шаблоны

Копируйте из `templates/lab.json` и `templates/task.json`.

## PDF методички

Файл с вариантами хранится у студента; при работе агент опирается на извлечённый текст или приложенный PDF в чате. Номер варианта **всегда 19**, если пользователь не указал другой.
